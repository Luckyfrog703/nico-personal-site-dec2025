Event Operations

Event Ops Planner

Run-of-show and event-day operations planner for venue event teams, built from five years running 200+ guest corporate events.

Problem

Buyouts for companies such as Salesforce, Apple, Meta, and Deloitte run off printed sheets, radio calls, and memory. There is no single source of truth, and issues solved verbally are lost.

Findings

Recurring failures are timeline drift, unclear staff assignments, and unlogged day-of issues. Radios are good for alerting but bad for structure, and the most valuable post-event record is the issue log.

Decisions

  • Minute-by-minute run-of-show with cue owners and one-tap statuses.
  • Staff assignments with call times and confirmations.
  • Vendor tracking: expected, arrived, set up, departed.
  • Prep checklist with a readiness percentage.
  • Day-of issue log with severity and resolutions.
  • In-app messaging and chat were cut on purpose; the app starts empty by design.

Outcome

A working app. Event cards show a countdown, prep progress, staff confirmations, and open issues, verified end to end.

Metrics

Percentage of cues completed in real time; issues logged per event; repeat-issue rate.

Roadmap

Version 2: templates for repeat event types and post-event report export. Version 3: read-only client view, then messaging once the core is sticky.

Game Production

Game Production Tracker

Production tracking for indie game teams: milestones, tasks, builds, and bug triage in one board.

Problem

Work is tracked across spreadsheets, chat, and untriaged bug lists. At indie scale, the producer's job has no single home.

Findings

Five surfaces carry nearly all daily work: milestone status, task board, build status, bug triage, and scope decisions. Scope calls made verbally or in chat and never recorded are where productions derail.

Decisions

  • Built exactly those five surfaces: a status board, milestones, a five-column task board, a build log (version, branch, QA status), severity-sorted bug triage with repro steps, and a decision log.
  • The app starts empty.

Outcome

A working app, verified end to end with a test production. Test data does not ship.

Metrics

Milestone slip rate; Sev-1 bug aging; decisions logged per milestone.

Roadmap

Version 2: milestone burndown and build-vs-milestone linking. Version 3: playtest notes tied to builds.

Product Management

PM Templates Hub

A working library of 30 product management templates, based on the Google PM Certificate document set, made fillable, saveable, and reusable.

Problem

New PMs learn documents as course exercises, then rebuild them from memory or hunt for random templates.

Findings

Documents cluster by lifecycle phase: initiation, planning, execution, and closing. A template alone is half the value; the other half is when to use it, who the audience is, and what good looks like.

Decisions

  • 30 templates organized by phase, with the Executive Report and Impact Report featured.
  • Each template includes when to use it, its audience, section instructions, worked example phrasing, and a pre-share checklist.
  • Use this template creates a fillable, saveable document with progress percentage, draft/final status, duplicate, and copy-as-text.

Outcome

A working app with search and filtering by phase, favorites, and a personal library. My Documents starts empty by design.

Metrics

Template completion rate; repeat use per user; favorites by phase.

Roadmap

Version 2: a starter pack flow. Version 3: export to Docs and Word.

Housing - Bay Area

Bay Area Rental Sifter

Sifts real Bay Area listings and automatically flags traps: Section 8 lotteries, senior-only buildings, income-restricted waitlists, and suspiciously cheap listings.

Problem

Affordable-looking listings routinely are not what they seem, and renters burn hours sorting through them.

Findings

Traps announce themselves in listing text (Section 8 welcome, 55+, BMR, lottery, income restricted). There is no clean public listings API, so the honest strategy is public sources that permit access, with cards linking back to the original post. A price far below comparables is a suspicion signal.

Decisions

  • Real listings only, no sample data.
  • RESTRICTED flags are hidden by default, with a toggle.
  • Suspiciously cheap - verify first warnings are benchmarked against the current batch.
  • A paste-a-listing checker highlights the exact red-flag phrases.
  • A shortlist pipeline: interested, contacted, touring, applied.

Outcome

A live app pulling about 190 real listings per refresh from public sources, refreshed automatically every morning. The first run caught a real SECTION 8 WELCOME listing and a below-market listing flagged from its body text. Disclosed imperfection: one RV-space post was labeled Studio because the source lists 0 bedrooms; it was still correctly flagged verify-first.

Metrics

Percentage flagged; checker usage; shortlist conversion to applied.

Roadmap

Version 2: alerts for new unflagged matches. Version 3: per-area typical-rent benchmarks.

Retail Prototype

Disney Store Merchandise Locator

A customer-facing prototype answering which store near me has this item? - a lookup employees have internally and customers do not.

Problem

Customers must call stores one by one to find an item.

Findings

The gap is exposure, not technology: inventory data exists internally. Five real California Disney Store locations from Disney's official directory (real addresses, hours, and phones) anchor the prototype.

Decisions

  • Search by full or partial item code or name.
  • Per-store stock sorted by distance, with in-store location info.
  • Directions and Call actions; category and in-stock filters.
  • A persistent Hunt List with notes.
  • Data honesty rule: Disney publishes no live customer inventory feed, so stock counts are sample data and the app says so on the page, with an About this prototype note explaining production integration through a retail inventory API.

Outcome

A working prototype with 5 real California locations and verified search and Hunt List flows.

Metrics

In production: search-to-directions conversion; zero-result searches as a demand signal.

Roadmap

Version 2: notify-me on arrival at a chosen store. Version 3: ship-to-store reservation.

Learning

Chess Tutor

Chess improvement for casual players: structured lessons, a tactics trainer, and games against a coach engine that grades every move.

Problem

Play engines crush beginners without teaching, and puzzle apps are disconnected from real games.

Findings

The improvement loop is: learn a concept, drill puzzles, apply it in a game, and get told what you did wrong in the moment. Move-by-move feedback beats post-game analysis for this audience.

Decisions

  • A six-lesson course (center control, forks and pins, discovered attacks, mating patterns, endgame opposition, middlegame planning), each on a real board.
  • Tactics Trainer: 10 puzzles with hints and explanations; every solution machine-verified.
  • Play the Coach: a from-scratch engine at three strengths that grades every move and flags blunders and hanging pieces.
  • Progress tracking persists.

Outcome

A working app. The engine, lesson answers, and all 10 puzzle solutions were verified programmatically.

Metrics

Lesson completion rate; puzzle retry rate; mistakes per game over time.

Roadmap

Version 2: personalized drills from the player's own blunders. Version 3: opening repertoire trainer.

Creative Tools

B-Roll Image Generator

A studio tool that turns a product brief into art-directed, photorealistic lifestyle images - showing the benefit in action, not the product on a shelf.

Problem

Small companies need lifestyle imagery. Photo shoots are out of reach, and stock never quite matches.

Findings

The creative unit is the benefit scene, not the product shot. A brief needs an editable art-direction step before rendering, because concepts are cheap and renders are expensive - mirroring brief, boards, shoot.

Decisions

  • Workflow: brief (company, product, benefit, audience, tone, frame format 16:9 / 1:1 / 9:16, scene count), then editable scene concepts, then real photorealistic renders.
  • Multiple takes per scene, with a Pick marker, download, and delete.
  • Brief library with cover frames and scene/frame counts.
  • Two starter examples: mood medication to morning tennis; dog food to a happy, healthy dog.

Outcome

A working app. The full pipeline was verified with real renders (a golden retriever bowl scene and Morning Tennis Rally). It starts empty.

Metrics

Brief-to-render conversion; picks per brief; re-direct rate.

Roadmap

Version 2: brand kits. Version 3: video b-roll from the same briefs.

Community - Feedback

Feedback Loop

A two-sided feedback platform where volunteers test things and give feedback - and can see the organizer respond and what changed.

Problem

Feedback tools are mailboxes. Volunteers submit into a void, never hear back, and stop participating.

Findings

From paid-study panels, participants never learn whether their feedback mattered. Retention is a product problem: people return when they can see their input change something.

Decisions

  • Two true sides in one app. Organizers post rounds (thing to test plus specific questions); volunteers rate, answer, and comment.
  • A shared thread, with organizer replies in the open and the ability to thank individuals.
  • A public You said, we changed board with because you said attribution.
  • Every round has a live loop-state badge: Collecting, Waiting on organizer, In discussion, Changes made, or Loop closed; the board tallies rounds waiting on the organizer.
  • It starts completely empty, with no fake volunteers or seeded praise.

Outcome

A working app. The full loop was verified end to end: post a round, volunteer response, organizer thanks and reply, change logged with attribution, and the round closed under Closed loops.

Metrics

Loop-closure rate; time-to-first-organizer-response; volunteer repeat-participation rate.

Roadmap

Version 2: volunteer profiles and round invitations, plus response themes and clustering. Version 3: scheduled organizer digest.
